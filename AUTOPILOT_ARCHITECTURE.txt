================================================================================
                     AUTOPILOT PLATFORM: SYSTEM ARCHITECTURE
================================================================================

This document provides the complete, end-to-end technical specification,
operational architecture, and structural layout of the Autopilot Platform.
Autopilot is an automated, self-healing, multi-tenant container orchestration
and deployment system designed to provision full-stack applications dynamically on AWS.

--------------------------------------------------------------------------------
1. COMPONENT TOPOLOGY
--------------------------------------------------------------------------------

The system is composed of two primary sub-systems cooperating over HTTP APIs and
asynchronous message queues:

2. DATA & CONTROL PIPELINES (THE PIPELINE SEQUENCE)
--------------------------------------------------------------------------------

A single deployment lifecycle transitions through the following precise stages:

[STAGE 1: INGESTION & ENQUEUEING]
* The User requests deployment via POST `/api/deployments` submitting repository details,
  AWS credentials mode, target environment parameters, and ports.
* The DeploymentController validates the token/session and user credentials.
* The record is saved in MySQL with a status of PENDING.
* The deployment ID is enqueued into the Redis-backed queue.
* The client immediately receives a 200 OK containing the pending Deployment entity,
  then opens an SSE connection to `/api/deployments/{id}/logs` to stream logs.

[STAGE 2: WORKER DEQUEUING & INITIALIZATION]
* A thread in DeploymentWorkerPool retrieves the deployment ID.
* The worker invokes CredentialResolverService to obtain credentials for AWS calls.
* The worker performs a git clone of the target repository to a temporary workspace.

[STAGE 3: REPOSITORY INSPECTION & CLASSIFICATION]
* ConfigIntelligencePipeline triggers the Repository Discovery phase.
* It scans directory trees for configuration files (pom.xml, package.json, requirements.txt, etc.).
* FrameworkRegistry classifies each discovered service (e.g. spring_boot, react_vite, angular, express).
* Roles are dynamically mapped:
  - Frontend frameworks (React, Angular, Static HTML) -> "frontend" role.
  - Backend/API frameworks (Spring Boot, Express, Django) -> "api" or "backend" role.
* Path allocations are determined:
  - The frontend is assigned a path prefix (e.g., `/app-xxxx`).
  - The API/Backend is assigned an API path prefix (e.g., `/app-xxxx-api`).

[STAGE 4: IMMUTABLE PLANNING]
* The deployment details are resolved into an ordered list of immutable DeploymentService objects.
* Database connections are analyzed: if a database dependency (e.g. MySQL) is detected,
  RDS provisioning is scheduled, and credentials are built.

[STAGE 5: PROVISIONING & INFRASTRUCTURE AUTOMATION]
* TerraformService spins up a workspace directory at `/tmp/autopilot-terraform/{deploymentId}`.
* It writes standard Terraform files and variables (`terraform.tfvars`) specifying custom VPCs,
  EC2 instances, security groups, and ingress rules.
* Terraform runs `terraform init` and `terraform apply` with a 3-attempt retry engine.
* AWS RDS provisions the database instance (if required).
* Connection credentials are saved in AWS Secrets Manager and exposed via an ECR-compatible format.

[STAGE 6: BUILD, CONTAINERIZE & REGISTRY PUSH]
* DockerBuilder dynamically constructs Dockerfiles for each classified service
  (unless a custom Dockerfile already exists).
* Docker compiles the container image and ECRPushService pushes it to AWS Elastic Container Registry (ECR).
* If a compilation error occurs, the Self-Healing Build Engine analyzes the logs:
  - Permission Error -> adds `chmod +x` to gradlew/mvnw wrappers.
  - Version Mismatch -> dynamically updates the target JDK/Node build version.
  - Dependency Mismatch -> appends options like `--legacy-peer-deps`.
  - Missing File -> triggers the generic fallback multi-stage Dockerfile.

[STAGE 7: REMOTE HOST DEPLOYMENT (SSM)]
* SSMDeployService connects to the target EC2 host via AWS Systems Manager (SSM).
* It pulls the docker images from AWS ECR.
* It runs the containers on the EC2 host within a shared docker network named `autopilot`.
* It assigns container-side listener ports and maps them to host-side dynamic ports.

[STAGE 8: NGINGX OUTER ROUTING CONFIGURATION]
* UniversalNginxGenerator generates a single, clean Nginx config for the EC2 host.
* It mounts strict namespace-based routes matching the designated prefixes:
  - `location /app-xxxx/` proxy passes to the frontend container.
  - `location /app-xxxx-api/` proxy passes to the backend/API container.
* It uploads this configuration to the host's Nginx service via SSM and restarts Nginx.

[STAGE 9: CONTAINER-LEVEL PATH NORMALIZATION (SPA REWRITING)]
* Inside static React/Vite SPA containers, Nginx needs to serve assets relatively.
* StaticSiteRuntimeStrategy injects a dynamic container-level rewrite rule:
  `rewrite ^/app-xxxx(/?.*)$ $1 last;`
  This strips the outer base-path routing prefix before Nginx matches static assets locally,
  preventing 404s for frontend resources.

[STAGE 10: HEALTH NEGOTIATION & VALIDATION]
* The startup StatefulWaitEngine polls the deployed application endpoint on the EC2 host.
* Post-deployment, CapabilityHealthVerifier performs a final HTTP request validation.
* To support microservices that lack explicit root health pages or default to redirects,
  both engines accept 200, 201, 202, 204, 301, 302, 307, 308, 401, 403, 404, and 405 response codes.
  An active server response of any kind verifies that the service is running and accessible.
* The deployment status is updated in MySQL to RUNNING.

3. AWS CREDENTIAL ROUTING ARCHITECTURE
--------------------------------------------------------------------------------

Autopilot ensures security isolation via dynamic credential mapping:

                    [Deployment Request]
                             |
                             v
               [CredentialResolverService]
                             |
         +-------------------+-------------------+
         |                                       |
   [MANAGED Mode]                         [BYOC Mode]
         |                                       |
   No AWS Role Arn                       Has Custom Role Arn
         |                                       |
   Use local instance                    Assume Role via AWS STS
   credentials directly                 (Duration: 3600 seconds)
         |                                       |
         +-------------------+-------------------+
                             |
                             v
                 [AwsCredentialsDto Resolved]
                             |
        +--------------------+--------------------+
        |                    |                    |
        v                    v                    v
  [RDS Client]         [Secrets Manager]      [SSM Client]

This architecture ensures that downstream clients never access hardcoded system
environment variables, preventing cross-tenant access.
